# 개발 구조와 우선순위

## 1 기본 결정

최신 기획서 v1.2의 정찰 SLAM, 자동 출발 정렬, 랜덤 물체, 깃발, SC, 페널티,
지정 추월, DRS, 후면 LED와 전면 LCD 랩타임을 유지한다. 아이템과 코너 보상은 마지막이다.
현장에서 확인하지 않은 토픽과 최고 속도를 코드의 기본값으로 채우지 않는다.

코드는 세 계층으로 나눈다.

1. core: ROS 없이 검증 가능한 경기 규칙과 데이터 계산.
2. adapter: ROS 메시지·Nav2 action·센서·드라이버 연결.
3. application: 정찰, 정렬, 경기 단계의 실행·운영.

ROS 2 Python 패키지는 setup.py/setup.cfg/package.xml을 사용하고,
사용자 메시지는 ament_cmake의 interfaces 패키지에서 생성한다.
제조사 코드는 src에 별도 저장소로 배치하며 버전을 고정한다.

## 2 패키지별 책임

| 패키지 | 소유자 | 구현 책임 | 직접 하지 않는 일 |
|---|---|---|---|
| core | C | 상태 규칙, 시간, 속도 정책, 표시 선택 | 센서·모터 I/O |
| interfaces | C/D | 메시지·서비스 계약 | 임의 필드 변경 |
| recon | A | 경계 추종, SLAM과 복귀 판단 | 경기 랩 판정 |
| navigation | A | 경로·구간, Nav2, 그리드 접근 | 경기 규칙 결정 |
| perception | B | 촬영·YOLO·신호·마커·거리 연관 | 최종 속도 출력 |
| behavior | C | 추종·추월·속도 제한 | SLAM 또는 모델 학습 |
| race | C | 경기 상태, 순위, 계시, 페널티 | 직접 바퀴 명령 |
| guard | D | 명령 제어권, timeout, 최종 정지 | YOLO 완료 대기 |
| display | D | LED·LCD, 랩타이머 표현 | 계시 규칙 재계산 |
| dashboard | D | 운영 입력·로그·화면 | 관제 단절 시 계속 주행 |
| bringup | D | 실행·설정·분리·배포 | 고정되지 않은 장비 가정 |

## 3 실행 배치

로봇에는 제조사 센서·모터, 로컬 guard, heartbeat 검사를 우선 배치한다.
정찰 SLAM·AMCL·Nav2의 로봇/PC 실행 위치는 실제 SBC와 부하를 측정해 확정한다.
YOLO는 PC 추론을 먼저 시험하되 로봇 내부 추론도 동일 계약으로 교체 가능하게 한다.
이 패키지에는 PC가 반드시 필요하다는 성능 결론이나 onboard 실시간 보장이 없다.
정찰 중 SLAM과 경기 중 AMCL의 TF 권한을 동시에 활성화하지 않는다.

## 4 최종 주행 명령

정찰·그리드·Nav2는 각각 cmd_vel 후보를 발행한다. command arbiter가 현재 단계의
한 소스만 선택한다. 속도 상한을 적용하고 가감속을 정리한 뒤 로컬 충돌 정지가 최종 검사한다.
최종 모터 토픽 발행자는 하나다. 정찰에서 그리드로 바뀔 때는 0 명령과 기존 제어권 해제를
확인한 뒤 전환한다. timeout은 timer로 검사하며, 새 명령 수신 때만 검사해서는 안 된다.
일반 감속과 비상 정지는 구분하고, 비상 정지를 낮은 감속 제한으로 지연시키지 않는다.

## 5 정찰 지도와 경기 경로

A 단독 정찰 → 루프 복귀 → 지도 검사 → map/path 버전 발행 → B 초기 위치 → 그리드 정렬.
map.yaml과 이미지, 최종 path.json, 체크포인트·구간, 좌표계·생성 시각·해시를 묶어서 전달한다.
주행 중 map pose를 그대로 연결하면 루프 폐쇄 시 끊어질 수 있다. 최종 지도 기반 중심선 또는
보정 궤적 하나를 선택해 재표본화하고, 경로 전체에서 로봇 외곽과 벽 간섭을 검사한다.
Nav2에는 연속 Path를 FollowPath로 전달하는 어댑터를 사용한다. 체크포인트마다
NavigateToPose로 멈추는 방식은 기본 경기 추종으로 사용하지 않는다. 장시간 루프를 어떻게
나누고 다음 구간을 연결할지는 S04에서 실제 action 동작으로 검증한다.

RPP는 추종 담당이다. 우회·추월 후보 경로 생성과 충돌 검사는 별도다.
RPP와 회피 생성이 어렵다면 MPPI를 비교하되 두 제어기를 무작정 동시에 구동하지 않는다.
DRS 속도 증가는 Nav2의 제어기 속도 상한과 함께 반영한다. 최종 Twist를 단순 배수로
키우지 않는다. 상한 해제와 unlimited의 의미는 설치 버전의 SpeedLimit 동작으로 확인한다.

## 6 상태 관리

경기 생애: IDLE → CHECKING → RECON → MAP_READY → GRID_ALIGN → STARTING → RACING
→ FINISHING → FINISHED. RED는 ABORTED로 이동하고 GREEN으로 복귀하지 않는다.
경기 제한: NORMAL/YELLOW/SC. 로봇별 행동: FOLLOW/CHECK/PASS/MERGE/ABORT 등.
정지 사유: ESTOP, FAULT, TIMEOUT, RED, PERSON, COLLISION, PENALTY, BLOCKED.
이 세 상태를 하나의 변수에 몰아넣지 않는다. 그린은 제한만 풀고 PERSON은 인식·거리
계층만, PENALTY는 페널티 관리자만 해제한다. ESTOP은 명시적 운영자 해제를 요구한다.

## 7 개발 방식

- 우선순위 0: 장비 정보·최종 정지·토픽·시간 계약.
- 우선순위 1: 정찰→지도→단독 주행. 이것이 주 경로다.
- 우선순위 2: 그리드·출발·두 대 기본 경기·기록.
- 우선순위 3: 랜덤 물체·깃발·SC·페널티·표시.
- 우선순위 4: 추종·지정 추월·DRS.
- 우선순위 5: 아이템·코너 보상.

B는 녹화 영상에서, C는 가짜 이벤트에서, D는 상태 재생에서 병행 개발할 수 있다.
모델 완성과 주행 완성을 서로 기다리지 않는다. 하드웨어 실행의 의존 단계와
독립적인 코드 개발 시작 조건은 다르다.

## 8 변경 규칙

메시지는 첫날 v0.1로 고정한다. 변경 시 발행자·구독자와 로그 재생 코드를 함께 수정한다.
단위는 m, s, rad, m/s, rad/s. 영상 좌표는 px로 표시한다. 유효하지 않은 값은 0으로
바꾸지 않고 validity를 함께 전달한다. race_id/map_id/path_id가 다르면 비교하지 않는다.
오프라인 가이드 구현과 미연결 하드웨어 adapter는 IMPLEMENTATION_MATRIX에 구분한다.
